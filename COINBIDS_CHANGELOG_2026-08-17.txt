PRIORITY 1 — PERSISTENT PER-USER DATA IN SUPABASE
============================================================

WHAT CHANGED
- New `public.coins` table in Supabase (see the .sql file), one row per
  Collection/Pending/Wishlist/Sold record, owned by `user_id` (auth.uid()).
- Row Level Security enabled with 4 policies (SELECT/INSERT/UPDATE/DELETE),
  every one scoped to `auth.uid() = user_id`. The database itself enforces
  this — not just the frontend.
- On login (after the country/profile gate passes), the app now loads the
  account's records from Supabase before showing the app shell.
- Every existing mutation path (add coin, add wishlist item, mark
  received/ordered, delete, sale split, Excel import) already funneled
  through the single existing `save()` function — that function now also
  pushes an upsert (and any needed deletes) to Supabase, in addition to its
  existing localStorage write. No new call sites had to be added anywhere
  else in the app for this to work.
- localStorage remains as a same-browser offline cache/fallback (used if
  Supabase is unreachable), exactly as permitted — it is no longer the
  authoritative store.
- Idempotent, ownership-safe migration: if Supabase has zero rows for an
  account and this browser has local data:
    - If that local data is already tagged as belonging to this exact
      account (an owner tag saved alongside it), it's migrated
      automatically.
    - Otherwise (ambiguous — could be a different account's leftover data
      on a shared computer), the person is asked explicitly before
      anything is uploaded into their account. Declining leaves the
      original local data untouched and starts the account empty.
  Once migrated, Supabase has rows, so this never re-triggers for that
  account — this is what makes it idempotent, not a separate "already
  migrated" flag.
- On logout, the local coins cache is now cleared (defense in depth against
  a later, different account on a shared browser ever seeing it) —
  Supabase is authoritative, so this costs nothing.
- "Reset my local data" was changed for signed-in accounts: it now RELOADS
  the account's real Supabase data (discarding only unsynced local
  changes) instead of deleting anything, since Supabase — not the
  browser — is now the real store. For a signed-out/offline session it
  behaves exactly as before.

BUG I FOUND AND FIXED DURING THIS WORK (not present in the final delivery)
While building this, I noticed that if "Reset my local data" had kept its
old delete-everything behavior for a signed-in user, the very next save()
afterward would have misread the reset as "the person deleted their entire
collection" and pushed matching deletes to Supabase — silently wiping the
account's real cloud data from a button literally labeled "local". Caught
and fixed before it reached you (see the changed behavior above).

WHAT WAS DELIBERATELY NOT DONE
- `offers` (Price Research results) were NOT added to Supabase — they
  remain a localStorage-only cache, same as before. The request was
  specifically about "Collection / Pending / Wishlist / Sold data"; adding
  offers persistence is a reasonable future addition but wasn't in scope
  here, and doing it silently would have been an unrequested schema/scope
  expansion.
- No UI indicator for sync status (e.g. "syncing.../saved") was added —
  functionally the sync is fire-and-forget after localStorage already has
  the data, so nothing is lost if you close the tab mid-sync (it retries
  next time coins[] changes and save() runs), but there's no visible
  spinner. Flag this if you want one added.

PRIORITY 2 — UNIVERSAL EXCEL WISHLIST IMPORT FIX
============================================================

WHAT CHANGED
- Root cause found: the importer had NO concept of a per-row "status"
  column at all. A single master sheet mixing OWNED/PENDING/WISHLIST rows
  via a Status column (exactly your example table) was previously always
  imported as one single status for the whole sheet.
- Added row-level status recognition:
  - A new value-based detector (importStatusFromValue /
    importStatusLike) recognizes OWNED/PENDING/WISHLIST/SOLD and
    reasonable English/Greek equivalents (collection/have/κατέχω,
    ordered/awaiting/παραγγελία, wishlist/wanted/desired/θέλω/επιθυμία,
    sold/πωλήθηκε).
  - This is matched by the CELL VALUE, not the column header name — a
    "Status" header is easy, but a "State" header is genuinely ambiguous
    (it's already used elsewhere in your sheets for numismatic grade, e.g.
    "State: VF") and is not blindly reused for status.
  - The column-profiling step that already auto-detects year/country/
    denomination/grade columns without relying on header names now also
    profiles for a status-like column the same way, so this works even on
    an arbitrarily-named column.
  - When a status column is found and a row's value is confidently
    recognized, that row's status overrides the sheet-level default;
    otherwise nothing changes from before.
- Added "desired" to the Wishlist sheet-name recognition (most of your
  requested name variants — Wish List, Want List, Wantlist, Wanted,
  Targets, Greek Επιθυμίες/Θέλω/Αναζήτηση/Λίστα επιθυμιών — were already
  covered by the existing detector before this pass; "Desired" specifically
  was the one genuinely missing).

WHAT WAS ALREADY WORKING (verified, not re-built)
- Dedicated Wishlist-named sheets (exact + fuzzy/semantic detection),
  arbitrary-named sheet inference via multi-signal scoring (name + headers
  + coin-like row content, avoiding a single stray mention of "wishlist" in
  unrelated text), and the import summary report were already correctly
  implemented before this pass.

PRIORITY 3 — NUMISTA API OPTIMIZATION (backend only)
============================================================

WHAT CHANGED (this pass, on top of the search-prefilter + 24h server cache
already shipped in a previous pass — both preserved, untouched)
- Request deduplication ("single-flight"): if multiple concurrent requests
  need the same not-yet-cached Numista type/issues at the same moment, only
  the first one calls Numista; the rest wait for that result. Tested with
  10 concurrent threads requesting the same coin → 1 real HTTP call (was 10
  before this fix).
- Rate-limit backoff: HTTP 429 responses are retried with a bounded backoff
  (honors a `Retry-After` header when Numista sends one; otherwise a short
  exponential backoff), capped at 2 extra attempts — never an unbounded
  retry loop. Numista's own docs confirm 429s exist but don't document
  specific custom rate-limit header names, so this uses the standard HTTP
  `Retry-After` convention rather than guessing a Numista-specific header.
